# بريف لكلود كود: تكامل Apex ECR (Cloud) ← Odoo 19

> **المهمة**: ربط Odoo 19 POS (خادم مركزي منفصل) بطرفيات MEPS Smart POS عبر Apex ECR بنموذج **Cloud-push**، بحيث يرسل الكاشير أمر SALE من Odoo، تصادق الطرفية، وتعود النتيجة تلقائيًا لسطر الدفع والإيصال.

---

## 0) القاعدة الذهبية (اقرأها أولًا)
- **لا تبحث في الويب عن مواصفة البروتوكول، ولا تُطلق subagents "تدوّر على مصادر".** تم التحقق: بروتوكول Apex ECR **غير منشور علنًا** (لا spec، لا Postman، لا GitHub). البحث هنا مضيعة وقت وهو سبب الطريق المسدود السابق.
- المجاهيل الثلاثة (endpoint + صيغة الطلب + التوقيع) تأتي **حصريًا** من وثيقة MEPS/Apex الرسمية. حتى تصل: عاملها كـ **config/parameters**، لا كشيء تكتشفه أو تخترعه.
- شغلتك الآن: بناء كل ما حول هذه المجاهيل، وعزلها خلف واجهة واحدة تُملأ لاحقًا بسطر واحد.

## 1) حقائق مؤكدة (اعتبرها معطاة — لا تُعِد التحقق منها)
- النموذج: **Cloud-push**. Odoo على خادم مركزي **منفصل** عن الأجهزة.
- تطبيق الطرفية: `com.apex.smartpos_meps` | APK `2.32.40` | SDK `2.15.0` | عتاد Newland **N950S** (Android 12).
- `https://gprs.mepspay.com:6610/apex.smartpos.gateway/services.ashx` = **uplink الطرفية نحو المضيف**، وليس قناة أوامر ECR. **لا توجّه الموصل إلى هذا العنوان.**
- **SecureKey لكل MID** (32 hex / 128-bit)، مفتاح واحد لكل MID. التاجر يملكها فعليًا. المفتاح = بيانات الاعتماد؛ الناقص فقط *كيفية استخدامه*.
- الأسطول: **7 MIDs / ~18 TID** موزّعة على الفروع. لكل فرع POS مستقل ← الموصل يختار TID حسب الفرع الحالي.
- العملة JOD ثلاثية العشرية (fils). الترميز **المرجّح** عدد صحيح × 1000 (3.500 ← 3500)، لكنه **غير مؤكد** ← اجعله parameter.
- حقول الرد المتوقعة (من إيصالات MEPS الفعلية): `approved` / `authCode(AUTH)` / `RRN` / `maskedPan` / `scheme` / `invoice` / `batch` / `AID` / `TVR`.

## 2) مجاهيل تأتي من MEPS/Apex فقط (لا تخترعها إطلاقًا)
1. الـ Cloud ECR endpoint لأمر POS→cloud (Base URL + Path + Port + Method) لـ SALE/VOID/REFUND.
2. صيغة الطلب: JSON/XML/Form + أسماء الحقول + بنية SALE + تمرير MID/TID + ترميز المبلغ.
3. آلية التوقيع بالـ SecureKey: HMAC/Hash؟ ترتيب الحقول؟ hex/base64؟ header أم حقل؟ timestamp/nonce؟
4. نموذج الانتظار (long-poll مقابل poll-by-id) + سلوك timeout.
5. رموز الأخطاء + بيئة sandbox + test TID.

**عند مواجهة أي من هذه**: ضع `# TODO(spec)` و parameter افتراضي، ولا تكتب قيمة مُخترعة تبدو حقيقية.

## 3) قيود معمارية غير قابلة للتفاوض
- **التوقيع وكل نداءات السحابة في الباك-إند (Python controller/service) فقط.** الـ SecureKey **لا يصل المتصفح/JS/QWeb أبدًا**. الواجهة تعرض حالة فقط ("بانتظار البطاقة… / تمّت / فشلت").
- **تخزين الأسرار**: مشفّر خارج الـ repo (env var أو `ir.config_parameter` مقيّد الوصول). أضِفه لـ `.gitignore`، ولا تكتبه في أي عيّنة/سجل/commit. نظّف history إن تسرّب.
- **طبقة عزل**: كل منطق Apex خلف كلاس واحد `ApexEcrClient` بواجهة ثابتة (`sale()`, `void()`, `refund()`, `status()`). عند وصول الـ spec، يتغيّر **هذا الكلاس فقط**.
- **Config-driven**: endpoint، خوارزمية التوقيع، ترميز المبلغ، أسماء الحقول ← كلها إعدادات، لا قيم مضمّنة (hardcoded).
- **Idempotency**: مرجع فريد لكل محاولة SALE (invoice ref)؛ منع الازدواج عند إعادة الإرسال بعد timeout — أخطر شيء في مسار الدفع هو خصم مرتين.
- **خارج نطاق PCI**: Odoo **لا يستقبل ولا يخزّن PAN** أبدًا. بيانات البطاقة تبقى على الطرفية (semi-integration). حافظ على ذلك.

## 4) خطة البناء (رتّب هكذا)
**الآن (لا يحتاج الـ spec):**
- Payment Method في POS بـ Integration = Terminal.
- نموذج `almond.pos.terminal` يربط: الفرع ← (MID, TID, SecureKey-ref).
- مخزن أسرار آمن + آلية جلب المفتاح حسب MID.
- كنترولر دفع (skeleton) + معالجة النتيجة (تعبئة RRN/AUTH/maskedPan/scheme على سطر الدفع والإيصال).
- واجهة POS: حالة الانتظار، زر إلغاء، مسار VOID، سلوك timeout واضح.
- Logging منظّم (بدون أسرار/PAN كامل).

**Stub (ليختبر الفلو كاملًا بدون endpoint حقيقي):**

**لاحقًا (فور وصول الوثيقة):**
- املأ endpoint + صيغة الطلب + التوقيع + تحليل الرد + خريطة الأخطاء داخل `ApexEcrClient` فقط.
